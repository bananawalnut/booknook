# Social implementation decisions

Date: 2026-10-10. Scope: the portable social protocol, native persistence, Nostr exchange, and Community interface. These decisions were made under the instruction to continue autonomously and leave a reviewable log.

| Decision | Reason and consequence |
| --- | --- |
| Add `booknook.social-state.v1` beside the existing reading archive | Existing notebook documents retain their meaning. Social processing contains only explicit selections, social drafts, and group discussions. It has no way to dereference a private notebook. |
| Use `social.execute` Castalia presentations for exact typed events | Friendship, publishing, list ownership, invitations, membership, and moderation all pass the same independently pinned credential verifier. A Nostr signature is never sufficient permission. |
| Record preparation time and approval time separately | Human consent and issuer requests take time. Historical verification uses the actual approval time, and accepts preparation at most 60 seconds before it. |
| Use the actual send time in the signed Nostr envelope | The enclosed Castalia receipt retains its exact approval time. An offline approval can be delivered after creating or renewing a transport binding. The envelope must not predate the approval; stable application identifiers deduplicate later retries. |
| Keep prepared drafts, consume receipt replay keys, and insert an outbox item in one SQLite transaction | A denied or cancelled consent cannot become a publication. A crash after approval retains the delivery request; relays must actually acknowledge it before removal. |
| Cancel pending content atomically on retraction or moderation | The original remains in private approved history but cannot be retried. A second outgoing check rejects stale imported retry copies for retracted IDs. Already acknowledged or in-flight copies cannot be recalled. |
| Rotate a bounded outbox scan with a persisted device cursor | Each exchange examines at most 200 records and attempts at most 50 sendable records. Invalid entries advance the cursor, so stale approvals or missing bindings cannot permanently starve later work. The queue offers a local stop-retrying action that preserves receipts and history. Scheduling position is device metadata, not portable authority. |
| Require mutual signed friendship intentions | A request is not a unilateral follow. Either reader can end the friendship; local blocking independently filters reception and recommendations. |
| Give lists a holder-scoped ID and explicit version | Only the creator may edit/delete, and stale edits are rejected instead of silently overwriting a newer list. |
| Make invitation, acceptance, and owner admission separate actions | A private invitation carries an owner-signed snapshot for the recipient. Private-group acceptance expresses the reader's consent; the owner then approves admission. Membership changes and bans advance the epoch. |
| Carry independently verifiable reader consent in private batch admissions | A new private acceptance explicitly permits its signed membership consent to be shown to current and future admitted group members. The owner includes these leaf acceptance receipts when admitting several readers; each receiver verifies holder/issuer signatures, group, epoch, expiry and the exact added readers. The original private invitation and discussions are never embedded. Legacy receipts keep their canonical bytes and are never silently redistributed; a fresh reviewed acceptance is required for a legacy reader in a batch. |
| Require a public membership request for public-group admission | Public observers can independently reconstruct group membership without inaccessible private invitation evidence. An encrypted invitation to a public group leads to the same reviewed public request. Requests expire after seven days or an epoch change. Owners can admit all waiting readers in one approved batch. The additional `join_requests` state field defaults empty when absent in earlier exports. |
| Encrypt private group deliveries separately for each intended recipient using NIP-44 | There is no unqualified shared group-key service. New discussions require the current epoch and current members. Revoked readers are excluded from subsequent content; removal notifications can still reach the previous audience. |
| Publish an explicitly approved Castalia-to-Nostr identity document | Public discovery can verify a new reader against the configured issuer pins. Unknown issuers are not automatically trusted. Version high-water marks prevent transport identity rollback. |
| Retain earlier binding proofs and retirement times | Renewing or replacing a key preserves authorized historical records. Sending requires the active key; an earlier transport key is accepted only for records before retirement, together with its exact Castalia proof. |
| Use application-data Nostr kind 30078 with unique identifiers | Each logical event has its own address; retries can be deduplicated. Public records use the `booknook` discovery tag. Private tags reveal recipient transport key and an opaque event digest, never group names or note text. |
| Keep catalog recommendations available without identity setup | Local catalog subjects and chosen interests require no Castalia policy. Shared ratings contribute only after the entire imported social projection is reconstructed from signatures under current issuer pins; absent or invalid trust falls back to catalog evidence only. Publication authorization is unchanged. |
| Keep private conversation content out of recommendations | Recommendations use the latest public rating/review per mutual friend and book, plus explicit catalog subjects. Repeated ratings cannot inflate the score. Every result explains its contributing evidence. |
| Run network work outside the Swift repository actor | Immediate editing and local persistence do not wait for relay timeouts. SQLite locks are released before network awaits; current membership and blocking are checked again before each send. |
| Reconstruct imported social projections from verified history before preparing, approving, or exchanging privileged actions | Portable files do not establish authority. Forged imported ownership/membership cannot prompt a legitimate signer to perform an unauthorized group operation. Configuration and secret keys are excluded from archives. |

The Community screen supports a chronological feed with spoiler hiding, reviewed publications, friendship requests/acceptance/revocation, owner-managed lists, public/private groups, invitations/admission/removal, moderator assignment and moderation, a durable queue, public-group discovery, recommendations, transport identity import/export, and local revocation. Every publication goes through the common Castalia consent UI. The complete reviewed record is shown as human-readable text, recipients, books, and effects within the existing Castalia text limits. The exact canonical event remains bound to the authorization receipt.

## Wire and privacy boundaries

The implementation uses the library's NIP-44 v2 codec inside signed Nostr events; the outer signature is verified before decryption. NIP-44 encrypts content but does not hide all relay metadata or provide forward secrecy. Book Nook caps an approved social record at 60,000 bytes and an encrypted wrapper at 65,535 bytes for interoperability and bounded allocation. [NIP-44 specification](https://github.com/nostr-protocol/nips/blob/master/44.md).

Private group content is stored locally in the private social store and is included in explicit private social-history/full portable exports. Public posting produces a separate selection with no private revision chain. A user's own group removals affect future access; previously decrypted history cannot be made unreadable on another person's device.

## Operational limits and qualification

- The current native settings pin one Castalia issuer/audience/caller/policy. Discovery accepts identities under that configured trust policy; arbitrary unknown issuers need an additional trust-provider configuration before their content can be accepted.
- A refresh fetches up to eight backwards pages of 500 events, rotates through at most 200 outbox records with at most 50 sendable attempts, and retains at most 1,000 dependency-blocked records. Only correctly bound and Castalia-approved input may enter the pending queue. Exceeding a bound is visible; no delivery success is fabricated. Timestamp saturation or older missing group history may require a narrower relay or an explicit portable import.
- Key revocation high-water marks and retirement times are local knowledge. Other participants must receive a newer approved binding or update their local trust policy to learn of a change. Existing authorized publications remain historical evidence.
- Nostr relay integration uses the actual SDK. An opt-in test passed against an independent pinned local relay with real acknowledgments, encrypted fetches, deduplication, a forced relay outage, desk reopen, and relay restart. It uses synthetic identities and local WebSockets; remote TLS, physical cross-device exchange, real identity-provider operation, and native Keychain lifecycle remain qualification tasks. See [local relay evidence and reproduction](../LOCAL-RELAY-VALIDATION.md).
- Native feed/list/group workflows compile as application code; build and UI verification results belong in the central validation log. A compilation result alone does not prove user-account integration.

## Reader-experience review

The first UI roundtable identified three accepted changes: public group composers must say anyone can read the discussion before text entry; discovery must lead with working offline book suggestions and offer a next action; sharing setup must be contextual instead of making local discovery appear blocked. Community now uses the same audience wording for the pre-composition label and the verified event's consent disclosure, opens local recommendations in the reading desk, explains empty/no-match/all-read states, and offers optional sharing setup after books. Outbox and sharing labels describe reader actions; protocol identifiers remain where needed to identify a connection.

The Library-to-Community review intent prefills saved text, stars, and reading status, expands the composer, and never publishes automatically. An unrated review stays unrated; a rating-only post requires choosing stars. Final UI acceptance is performed by the coordinating task, which alone controls the native app. These Swift changes require no Rust contract or dependency change.

The bounded third review found and fixed a draft-loss failure: retry previously deleted the saved draft before preparing its replacement. Retry now preserves the original until a replacement is committed to the native store. Failed preparation or persistence keeps the original; declined consent or failed approval keeps the replacement. Explicit consent cancellation is quiet, while denied or expired authorization still reports its cause. `scripts/test-ui-workflows.sh` compiles the actual application controllers with the native bridge and exercises missing-authority retry against SQLite: it failed before the fix at draft retention, then passed with the original Unicode draft intact after reopening and no publication or outbox entry created. This is headless workflow evidence, not live screen or account qualification.
